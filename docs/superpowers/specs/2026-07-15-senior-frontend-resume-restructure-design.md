## 1. 目标与定位

本次重构面向以下求职目标：

- 主要岗位：高级前端开发工程师。
- 次要岗位：Web3 Frontend Engineer。
- 优先公司类型：支持国内远程协作的团队。
- 地域：成都现场或国内远程。
- 核心定位：通用 Senior Frontend，Web3 是差异化优势，不把候选人限制为只能投递 Web3 岗位。
- 希望形成的第一印象：能独立负责复杂 Web3 产品，同时兼顾业务交付、前端架构和团队协作。
- 弱化方向：Android 和传统外包经历只承担职业连续性证明，不占据核心版面。

简历不为某一份具体 JD 定制。它是后续生成一页 JD 定向版的事实主稿，所有表述应能在面试中解释并经得起追问。

## 3. 方案比较与选择

### 方案 A：两页证据优先主简历（采用）

第一页突出职业定位、能力栈、近期项目和负责人证据；第二页补足 NFTScan 成果、早期经历和教育信息。

优点：能容纳 11 年以上职业经历和三个主要 Web3 项目的差异化成果；事实密度高；既适合通用 Senior Frontend，也保留 Web3 竞争力。缺点：需要严格控制每个项目的要点数量，避免第二页成为项目堆砌。

### 方案 B：一页高度压缩版

优点：扫描速度快，适合单一 JD 和内推转发。缺点：会牺牲团队负责人证据、NFTScan SDK 数据和复杂交互细节，不能作为完整事实主稿。

### 方案 C：两页 Web3 项目型简历

优点：链上交互和多钱包能力最突出。缺点：容易把候选人定位成只适合 Web3，偏离“通用 Senior Frontend，Web3 是优势”的目标。

因此采用方案 A；方案 B 后续从主简历裁剪生成，方案 C 不作为本次输出。

## 4. 内容架构

### 4.1 第一页

1. 姓名与联系方式

2. 求职标题
   - `高级前端开发工程师｜React / Next.js / Web3`
   - 不把 `Web3 Frontend Engineer` 放在唯一职位标题中，避免限制非 Web3 投递。

3. 职业摘要
   - 11 年以上前端与客户端开发经验，其中 4 年以上 Web3 产品经验。
   - 能独立负责复杂产品从需求评审、技术方案、任务拆解、开发、Code Review 到发布和线上维护的完整闭环。
   - 具备 React / Next.js / TypeScript、EVM / Solana、多钱包和复杂交互经验，并有跨城市远程团队协作证据。
   - 摘要控制在 3 条，不使用“精通”“专家”等不可验证形容词。

4. 核心技能
   - 前端：TypeScript、JavaScript、React、Next.js、Vue、Angular、Zustand、Tailwind CSS。
   - Web3：EVM、Solana、wagmi、viem、ethers.js、RainbowKit、Dynamic Labs、`@solana/web3.js`。
   - 工程与交付：Git、Vercel、Webpack / Rollup、Playwright / Vitest、Nest.js、CI/CD、Code Review。
   - 仅保留可从工作项目或代码仓库解释的技能，不以工具罗列代替成果。

5. 工作经历概览
   - NFTScan 产品团队：`核心前端开发 / 项目前端负责人`，`2022.06–至今`。

   - Android 相关经历合并或压缩到最小必要篇幅。

6. 重点项目：1DEX

   - 从 0 到 1 负责 Reward / Referral 模块，包括钱包签名登录、邀请关系、EVM / Solana 地址绑定、链上奖励领取、状态管理、多语言和移动端适配。

## 5. 表述原则

- 每条项目经历采用“职责/动作 + 技术难点 + 可验证结果”的结构。
- 一条要点只表达一个主要结论，避免同一条堆叠五种技术名词。
- 优先使用“独立负责”“前端负责人”“核心前端开发”“从 0 到 1”“按期上线”等已确认责任用词。
- 团队负责人和项目负责人严格按项目区分；不能把 Mint、1DEX 的负责人身份外推到 NFTScan。
- 将“参与”替换为具体职责，但没有明确 ownership 时不使用“主导”。
- 数字必须带口径；范围数据保持范围，不推导精确值。
- 不把代码行占比、commit 数量直接写入投递版；这些只作为归属证据，在面试或附属材料中使用。
- 不以 AI coding agent 作为摘要核心能力；如版面紧张则删除。
- 不添加自我评价、兴趣爱好、照片、性别、年龄、期望薪资或无法证明的软技能。

## 6. DOCX 视觉与 ATS 规则

- A4 两页，固定页数目标，不通过极小字号强行压缩。
- 正文优先使用 9.5–10.5 pt，一级标题 12–14 pt，姓名 20–24 pt。
- 使用本机可渲染的 CJK 字体；优先 `Hiragino Sans GB`，英文和数字使用兼容的无衬线字体。
- 使用单栏排版、普通段落、项目符号和右对齐制表位；避免复杂表格、文本框、图标字体和多栏布局，以提高 ATS 解析稳定性。
- 使用克制的深蓝或深青色作为标题色，正文保持黑色，确保黑白打印仍有清晰层级。
- 联系方式使用纯文本，不嵌入不可解析图标。
- 页首不重复装饰性 Header；第二页保持项目标题和段落连续，不制造大量空白。
- 不直接覆盖现有简历。新产物写入独立输出目录。

## 8. 实施与验收

设计确认后，实施计划必须覆盖：

1. 从现有材料提取不可变个人信息和早期工作经历。
2. 按本规格编写完整中文 Markdown 主稿。
3. 逐条检查项目日期、角色、团队规模、技术栈、责任范围和量化口径。
4. 使用 `python-docx` 生成 DOCX，设置 A4、段落间距、分页规则、字体和制表位。
5. 使用仓库环境提供的 DOCX 渲染脚本或 LibreOffice 生成逐页图片。
6. 视觉检查每一页，确认无乱码、溢出、孤行、异常分页、密度失衡和过小字号。
7. 用文本提取再次核对关键日期和数字，确认 ATS 可读取。
8. 输出 Git scope、实际执行命令、渲染结果、已知限制和未执行项。

验收标准：

- 产物严格为两页 A4。

- 1DEX、Mint Blockchain、NFTScan 的日期、角色和 ownership 不冲突。
- 所有量化数字都有明确来源和口径，不出现无依据指标。
- 第一页在不阅读第二页的情况下，已能建立“Senior Frontend + Web3 + 独立交付 + 负责人”的核心印象。
