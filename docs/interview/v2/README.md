## 事实标签合同

| 标签 | 能证明什么 | 不能外推什么 |
| --- | --- | --- |
| `[候选人确认]` | 本人明确确认过的职责、经历或结果 | 不能省略口径，也不代表有公开源码 |
| `[简历事实]` | 当前主简历中的陈述 | 不能自动证明具体实现细节或个人独占成果 |
| `[源码可证]` | 当前仓库、配置、测试或文档可直接验证的状态 | 不能证明历史线上版本也相同，不能证明代码都由本人完成 |
| `[通用原理]` | 框架、浏览器、协议和工程知识 | 不能说成项目实际采用过 |
| `[设计提案]` | 面对假设问题时可执行的方案 | 只能用“我会”“可以”“先验证”表达 |
| `[待补 STAR]` | 题目适合使用真实事件回答，但现有材料不完整 | 补齐前不能编造时间、影响、动作或量化结果 |

答题时优先把标签翻译成自然语言，不必向面试官念标签。例如：

- `[候选人确认]`：“我在 1DEX 的实际职责是……”
- `[源码可证]`：“当前作品集仓库可以验证的是……”
- `[通用原理]`：“从 React 的运行模型看……”
- `[设计提案]`：“如果让我重新设计，我会先……”
- `[待补 STAR]`：“我需要用一个真实事件回答，不能只讲原则。”

## 三条强制边界

### 1. 角色边界

- `[候选人确认][简历事实]` 1DEX、Mint Blockchain：前端负责人。
- `[候选人确认][简历事实]` NFTScan：核心前端开发，不是前端负责人。
- 产品用户量、SDK 下载量和团队交付是规模证据，不等于个人独占成果。

### 2. 项目边界

- `[候选人确认][简历事实]` 历史 Mint Forest v3 是线上 Web3 产品，候选人在 2025.03～2025.04 一个月内独立完成全部前端并按期上线。
- `[源码可证]` 当前仓库中的 `/mint-forest` 是去链上化、本地 mock、确定性持久化的作品集演示。
- 当前仓库能证明交互结构和现在采用的工程方法，不能反向证明 2025 年生产版本已经具备相同测试、目录隔离或 mock 设计。

### 3. 版本边界

- `[源码可证]` 当前仓库使用 Next.js 15.2.6，路由以 Pages Router 为主。
- `[通用原理]` 本文技术复习基线更新到 2026-07-15；当前 Next.js 文档中的 `Proxy` 是原 `Middleware` 文件约定的新名称。讨论历史项目时仍按当时版本和真实实现回答。
- `[通用原理]` React Effect 通常在 commit 后运行，但由交互触发的 Effect 可能在浏览器绘制前执行；需要阻止闪烁或测量布局时考虑 `useLayoutEffect`。
- `[通用原理]` EIP-5792 和 EIP-7702 不是同一个协议：前者是钱包调用批处理接口，后者通过 authorization list 为 EOA 设置持久代码委托。项目是否使用某字段必须以当时钱包与代码为准。

## 回答结构

默认使用“结论—证据—边界”三段式：

1. **结论：** 先回答问题，不从背景绕起。
2. **证据：** 给一个项目动作、技术约束或可量化事实。
3. **边界：** 说明哪些是团队结果、哪些未公开、哪些只是设计判断。

行为题改用 STAR，但只说已补齐的真实事件。技术题先讲运行模型，再讲取舍；项目题先讲个人 ownership，再讲团队与结果。

## 完成标准

面试前至少做到：

- 24 个 P0 都能在 30 秒内给出结论。
- 1DEX、Mint Forest、NFTScan 各有一个 60～90 秒版本。
- 8 个 STAR 槽位中至少补齐 6 个真实故事，并能指出证据。
- 能解释所有数字的统计口径和个人贡献边界。
- 遇到未做过的技术时，能准确区分“理解原理”“做过类似问题”“实际生产使用”。
