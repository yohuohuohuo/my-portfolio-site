## C. React、Next.js、性能与工程（6 题）

### P0-12｜React 从 render 到 Effect 的过程是什么

**30 秒短答**

React 先在 render 阶段计算下一棵 UI，这个阶段应保持纯函数且可能被中断或重做；commit 阶段把变化应用到 DOM，并处理 ref。`useLayoutEffect` 在浏览器重绘前执行且会阻塞绘制，`useEffect` 通常在绘制后执行，但交互触发的 Effect 可能在绘制前运行，所以不能把它概括成绝对“paint 后”。

**90 秒展开**

强调 state 是一次 render 的快照，闭包读取的是当次值；基于前值更新应使用函数式 setter。Effect 用于同步外部系统，不用于推导可在 render 中计算的数据。开发模式 Strict Mode 会额外执行一次 setup / cleanup，帮助暴露清理不对称问题，不等于生产重复执行。

**证据边界**

`[通用原理]`。项目中是否遇到具体 Effect 问题必须另给真实例子。

**高概率追问**

### P0-13｜如何正确使用 useEffect，怎么避免依赖和竞态问题

**30 秒短答**

先判断是否真的需要 Effect：如果只是从 props / state 推导值，直接 render 计算；用户动作放事件处理器。Effect 只同步外部系统，依赖必须完整，setup 与 cleanup 对称。异步请求用 `AbortController` 或忽略过期响应，避免旧请求覆盖新状态；不要靠关闭 lint 或手写不完整依赖逃避模型问题。

**90 秒展开**

对象或函数依赖频繁变化时，先移动到 Effect 内、提升稳定边界或重构数据流，再考虑 `useMemo` / `useCallback`。订阅、定时器、observer 和事件监听必须清理。服务端数据优先使用框架数据层或查询库管理缓存、去重与竞态，不把每个请求都写成裸 Effect。

### P0-15｜Pages Router 与 App Router 怎么选，如何处理版本差异

**30 秒短答**

两者不是简单的新旧替换。App Router 提供 Server Components、嵌套 layout、流式渲染和新的数据边界，但增加缓存、序列化和 client boundary 的复杂度。存量 Pages Router 项目只有在收益明确、依赖兼容和验证基线具备时才渐进迁移。当前作品集是 Next.js 15.2.6、以 Pages Router 为主，我不会声称做过大规模 App Router 生产迁移。

**90 秒展开**

### P0-16｜如何解释 SSR、hydration 和缓存问题

**30 秒短答**

SSR 先在服务端生成 HTML，hydration 在客户端让同一棵 UI 接管交互。首个客户端 render 必须与服务端输出一致；直接读取 `window`、时间、随机数、locale 或本地存储都可能造成 mismatch。缓存必须先区分请求去重、数据缓存、路由输出缓存和客户端查询缓存，再说明失效条件，不能只说“Next 会自动缓存”。

**90 秒展开**

对浏览器专属值可延后到 Effect、使用稳定服务端快照或拆成 client-only 区域，但不能随意用 `suppressHydrationWarning` 掩盖结构差异。缓存设计围绕数据新鲜度、用户隔离和 mutation 后失效：公开低变数据可缓存，账户或权限数据必须避免跨用户复用；任何结论都以所用 Next.js 版本和路由模式为准。

**证据边界**

`[通用原理]`。当前作品集的实际缓存策略不是历史项目缓存经验的替代品。

**高概率追问**

- hydration mismatch 如何定位？
- 登录用户数据为什么容易缓存串号？

### P0-17｜你如何做前端性能与质量验证

**30 秒短答**

先定义用户路径和预算，再按加载、渲染、交互和稳定性分层测量。加载看 LCP、资源瀑布和关键 chunk；交互看 INP、长任务和 render；布局看 CLS；Canvas 看帧耗时、对象数量与低端机。优化后要在相同条件重测，并用单元、集成、E2E 和线上监控覆盖不同风险。

**90 秒展开**

方法是“测量—归因—最小改动—回归”：用 Performance panel、React Profiler、bundle analyzer 和真实设备找瓶颈；再选择路由分包、资源压缩、减少无效 render、虚拟化或移出主线程等手段。测试按风险分层：纯规则和精度做单元，状态与数据边界做集成，登录、关键 mutation 和移动手势做 E2E。构建通过不等于浏览器验收通过。

**证据边界**

`[通用原理]`；`[源码可证]` 当前作品集有 Vitest 和 desktop / mobile Playwright。不能把当前测试覆盖全部归为 2025 年生产版本成果，也不能编造历史覆盖率。

## D. Web3、数据精度与系统设计（7 题）

### P0-18｜EVM 和 Solana 前端模型的核心差异是什么

**30 秒短答**

EVM 常以账户、合约调用、nonce、Gas 和 receipt 为中心；Solana 以账户集合、instruction、recent blockhash、fee payer 和 transaction message 为中心。前端可以统一业务状态与错误模型，但不能抹平地址、单位、费用、授权、交易大小和确认机制差异。

**90 秒展开**

EVM 侧要处理 chainId、allowance、用户拒签、replacement 和 receipt；Solana 侧要处理 ATA、account metas、blockhash 过期、Legacy / V0 message、ALT 和 commitment。公共层可以统一“准备—签名—提交—确认—聚合”，adapter 暴露每条链的能力与限制。完全统一会让异常变得不可解释。

**证据边界**

`[通用原理][简历事实]` 候选人做过 EVM / Solana 多链产品；具体错误码与确认策略以真实项目实现为准。

### P0-19｜链上金额为什么不能直接使用 JavaScript Number

**30 秒短答**

链上金额通常是最小单位整数，可能超过 `Number.MAX_SAFE_INTEGER`；一旦中间转换成 `Number`，比较、加减和提交参数都可能静默丢精度。内部用 `bigint`、大数库或十进制字符串保存，按 token decimals 做字符串级 parse / format，只在图表等允许近似的展示边界转浮点数。

**90 秒展开**

输入解析要拒绝超出 decimals 的位数，业务比较保持同一单位，序列化时显式转字符串；格式化不能先除成浮点数。测试覆盖安全整数边界、极大值、零、负数、前导零、最大 decimals 和舍入规则。API、store、组件 props 和合约调用之间需要统一金额类型，避免局部修复。

**证据边界**

`[通用原理]`。现有材料不能证明发生过真实线上精度事故；在补齐故事库前，只能说这是识别并防范的风险，不能说“我曾导致线上损失”。

**高概率追问**

- `bigint` 为什么不能直接 JSON.stringify？
- 用户输入 `0.0000001` 如何转最小单位？

### P0-20｜如何设计可靠的交易状态机和异常恢复

**30 秒短答**

不能把“钱包已返回 hash”当成成功。我会把 prepared、awaiting-signature、submitted、confirmed、failed、cancelled 等状态显式建模，保存能恢复查询的订单号、batch id 或 hash。错误按用户拒绝、参数错误、余额不足、RPC 暂时故障、链上失败和未知状态分类，只有确认安全且幂等时才允许重试。

**90 秒展开**

每次 mutation 先生成幂等键，提交前记录意图，返回标识后持久化；页面刷新后从后端订单或本地恢复轮询。批量交易按单项保存状态，并提供部分成功的明确反馈。超时只代表客户端停止等待，不等于链上失败；重试前先查询原交易，避免重复执行。

**证据边界**

`[通用原理][设计提案]`；1DEX 已确认有订单提交、状态轮询和异常反馈，但精确状态枚举与持久化位置必须以真实代码为准。

**高概率追问**

- RPC 返回超时后如何判断是否重试？

### P0-21｜EIP-5792 与 EIP-7702 分别解决什么问题

**30 秒短答**

EIP-5792 定义钱包调用批处理 API，包括能力查询、`wallet_sendCalls` 和状态查询；当前请求关注 `version`、`chainId`、`atomicRequired`、`calls` 与 capabilities，原子能力状态包括 `supported`、`ready`、`unsupported`。EIP-7702 增加带 authorization list 的交易类型，为 EOA 设置持久代码委托。两者可以被钱包组合使用，但不是同一协议，也不能把 7702 说成批量 RPC。

**90 秒展开**

应用先通过 `wallet_getCapabilities` 探测链和钱包能力，满足时调用 `wallet_sendCalls`，保存返回 id 并通过 `wallet_getCallsStatus` 查询；不支持时根据业务选择逐笔 `eth_sendTransaction` 或明确阻止。即使请求原子执行，应用也不应假设所有调用一定落在单笔普通交易里。历史 1DEX 使用方式还受当时 MetaMask / OKX 实现约束。

**证据边界**

`[通用原理]` 当前规范字段；`[简历事实]` 1DEX 接入过 MetaMask EIP-5792 和 OKX `executeFromSelf`。不要把 2026 年规范字段全部倒推为当时项目实现。

**高概率追问**

- 钱包不支持 `wallet_sendCalls` 怎么降级？
- `atomicRequired` 为 `false` 时 UI 如何表达部分结果？

### P0-22｜Solana 的 ATA、V0 Transaction 和 ALT 是什么

**30 秒短答**

ATA 是由 wallet 与 mint 等种子确定的标准 Token Account，接收方没有时可能需要先创建。V0 Transaction 使用 versioned message，可引用 Address Lookup Table，把账户地址从交易消息移到链上表中，降低大量账户地址占用；它不能消除 instruction 数据、签名数量和计算预算等其他限制。

**90 秒展开**

构建交易前先检查 ATA 是否存在，并决定创建成本由谁承担；收集全部 instruction 后估算消息大小与账户数量，Legacy 足够时保持简单，超限再使用 V0 / ALT。ALT 还涉及表的创建、扩展、激活与可用性，不适合为了“新”而默认启用。批量 Token 操作必须同时考虑 transaction size、compute units、blockhash 过期和钱包兼容。

**证据边界**

`[通用原理][简历事实]` 1DEX 有 ATA、Legacy / V0 和 ALT 处理经验；具体表由谁维护、阈值和重试策略按真实实现回答。

**高概率追问**

- ATA 创建与业务 instruction 能否同一笔提交？

### P0-23｜如何兼容多钱包能力差异和批量部分失败

**30 秒短答**

先探测能力，不按钱包名称硬编码乐观假设。adapter 返回支持的链、批量方式、签名约束和状态查询能力；业务层只依赖统一接口，但 UI 必须保留能力差异。批量结果按单项建模，明确成功、失败、取消和未知，不用一个 toast 把部分失败伪装成整体成功。

**90 秒展开**

能力探测失败时采用保守降级：能逐笔安全执行就提示成本和签名次数，不能保证语义就阻止。错误标准化时保留 raw error 便于诊断；同一钱包不同版本和链的能力也可能不同，所以缓存要有作用域和刷新策略。重试只重试确认未成功且满足幂等条件的项。

**证据边界**
