# 02｜真实项目与 STAR 故事库

## 使用规则

行为题不能只讲原则，也不能把合理设计改写成个人经历。一个可用故事必须同时回答：具体发生在什么时候、目标是什么、你本人做了什么、结果如何验证、复盘后改变了什么。

本文中的 `[待本人补充]` 是刻意保留的真实性门槛。未补齐的故事只能用于识别准备缺口，不能直接作为面试答案。

## 二、STAR 故事最小证据

至少准备以下一种佐证，即使不能向面试官展示，也要能让自己复述一致：

- 当时的需求、任务、Issue、PR 或发布记录。
- 能说明决策的技术文档、架构图、接口合同或 Review 意见。
- 能复现问题和修复前后差异的错误日志、监控或测试。
- 可解释口径的产品统计，不使用无法说明来源的整数或百分比。
- 与同事分工一致的 ownership 描述。

### STAR-01｜紧期限下完成复杂交付：Mint Forest v3

**适用问题：** 一个月完成是否赶工；如何排优先级；如何保证质量。

- **Situation：** `[候选人确认][简历事实]` 2025.03～2025.04，Mint Forest v3 需要在一个月内完成全部前端并上线。更具体的业务期限原因、已有基础和人员约束为 `[待本人补充]`。
- **Task：** `[候选人确认][简历事实]` 本人负责需求讨论、技术选型、全部前端实现、开发验收、Vercel 多环境发布和后续维护。明确后端、合约、设计、测试各自由谁承担 `[待本人补充]`。
- **Action：** `[待本人补充]` 用真实顺序写出如何切 MVP、识别关键链路、复用公共状态与组件、安排 Preview 验收，以及主动砍掉或延期了什么。
- **Result：** `[候选人确认][简历事实]` 按期上线；上线后三个月累计注册 40 万以上，Campaign 峰值日活数万。补充质量信号、上线问题或回滚情况 `[待本人补充]`。
- **证据：** 项目时间、发布记录、需求范围、本人负责模块、指标口径 `[待本人补充]`。
- **禁说项：** “一个人完成整个产品”“零故障”“没有技术债”“40 万用户都是我的增长成果”。
- **30 秒结构：** 一个月期限 → 我负责全部前端 → 如何切核心链路 `[待本人补充]` → 按期上线与正确数据口径。
- **90 秒加深：** 补充一个主动取舍、一个质量 gate、一个上线后复盘；三项均需真实事实。

### STAR-02｜推动一次技术分歧达成决策

**适用问题：** 与同事意见不一致怎么办；负责人如何决策；如何避免独断。

- **Situation：** 项目、时间、参与角色、分歧主题 `[待本人补充]`。优先选择 Canvas / DOM、批量交易抽象、状态管理或发布方案中的真实案例。
- **Task：** 当时必须做出的决策、截止时间和成功标准 `[待本人补充]`。
- **Action：** 双方方案、你收集的数据、最小验证、风险清单、谁做最终决定 `[待本人补充]`。
- **Result：** 采用了什么方案、交付或维护结果、是否出现反例 `[待本人补充]`。
- **证据：** 方案文档、benchmark、PR 讨论、原型或回顾记录 `[待本人补充]`。
- **禁说项：** “我证明对方错了”“因为我是负责人所以按我的方案”“大家最后都同意”。
- **30 秒结构：** 具体分歧 → 共同标准 → 小实验或证据 → 决策结果。
- **90 秒加深：** 说明对方方案的合理部分、你的初始判断是否修正、决策如何记录。

### STAR-03｜处理一次真实线上故障

**适用问题：** 最严重的线上问题；如何止损；如何复盘。

- **Situation：** 项目、发生时间、用户可见症状和发现渠道 `[待本人补充]`。
- **Task：** 你在故障中的角色、优先级和沟通对象 `[待本人补充]`。
- **Action：** 如何确认影响、止损、定位、修复、验证和恢复；时间线 `[待本人补充]`。
- **Result：** 影响持续时间、受影响范围、恢复证据和后续预防项 `[待本人补充]`。
- **证据：** 监控、日志、错误样本、发布记录、复盘或测试 `[待本人补充]`。
- **禁说项：** 把大整数原理虚构成事故；没有来源的损失金额；“以后加强测试”这种无措施结论。
- **30 秒结构：** 影响 → 止损 → 根因 → 修复与预防。
- **90 秒加深：** 分开触发条件、根因和扩大因素；说明哪些判断当时错误。

### STAR-04｜估期变化或需求中途扩张

**适用问题：** 无法按期怎么办；如何管理预期；如何处理频繁变更。

- **Situation：** 项目、原范围、原估期和变化发生点 `[待本人补充]`。
- **Task：** 必须守住的业务目标和不可妥协的质量边界 `[待本人补充]`。
- **Action：** 如何重估、拆 Must / Should、暴露依赖、提出替代路径、同步干系人 `[待本人补充]`。
- **Result：** 最终交付范围、时间和后续补齐情况 `[待本人补充]`。
- **证据：** 版本计划、任务变更、验收清单或上线记录 `[待本人补充]`。
- **禁说项：** “加班解决一切”“产品一直变”“最终都做完了”但说不出范围。
- **30 秒结构：** 变化事实 → 影响分析 → 三个选项 → 对齐后的结果。
- **90 秒加深：** 说明估期方法哪里失准，以及下一次如何提前暴露同类风险。

- **Task：** 你作为负责人需要恢复什么节奏、避免什么风险 `[待本人补充]`。
- **Action：** 如何补齐接口或验收合同、拆小任务、调整 owner、设置升级机制和回写决策 `[待本人补充]`。
- **Result：** 阻塞解除时间、版本影响、流程改动是否持续采用 `[待本人补充]`。
- **证据：** 任务系统、接口文档、会议结论或 Review 记录 `[待本人补充]`。
- **禁说项：** 把成员描述成不负责；用在线时长替代交付；只说“多沟通”。

### STAR-06｜帮助同事提升交付质量

**适用问题：** 如何培养成员；Code Review 的价值；如何处理反复犯错。

- **Situation：** 具体成员面临的技术或交付困难 `[待本人补充]`，不得透露敏感身份。
- **Task：** 希望提升的能力和可观察标准 `[待本人补充]`。
- **Action：** 你如何示范拆解、结对、Review、给反馈并逐步放权 `[待本人补充]`。
- **Result：** 对方后来能独立完成什么、返工或 Review 质量如何变化 `[待本人补充]`。

- **禁说项：** 编造晋升、绩效和培养人数；把团队正常协作包装成导师成果。
- **30 秒结构：** 明确短板 → 给方法与反馈 → 逐步放权 → 可验证变化。
- **90 秒加深：** 说明你根据对方反馈调整了什么，而不是单向教学。

### STAR-08｜识别并治理数据精度风险

**适用问题：** 犯过什么技术错误；如何处理大整数；一次深刻复盘。

- **Situation：** 现有材料只能确认链上金额存在精度风险，不能确认真实线上事故。具体项目、代码路径、发现方式 `[待本人补充]`。
- **Task：** 需要保护的金额、比较、展示或交易参数边界 `[待本人补充]`。
- **Action：** 是否将 `Number` 改为 `bigint` / 字符串 / 大数库，如何统一 parse / format、类型和边界测试 `[待本人补充]`。
- **Result：** 修复了哪些路径、是否发现历史错误、如何证明没有回归 `[待本人补充]`。
- **证据：** bug、PR、测试、数据样本或 Review 规则 `[待本人补充]`。
- **禁说项：** 在没有事件证据时说“我造成过线上金额错误”；编造损失；只背 `MAX_SAFE_INTEGER`。
- **30 秒结构：** 如果故事已补齐：风险出现 → 根因在公共边界 → 统一类型与测试 → 复盘。未补齐时不要把它当行为题答案。

## 四、补齐后的自检

每个准备上场的故事都应能回答“是你亲自做的吗”“同事会如何验证”“结果口径是什么”。若任何一项只能用模糊措辞回答，就继续补事实或换故事。

优先完成顺序：STAR-01、STAR-03、STAR-02、STAR-05、STAR-06、STAR-04；STAR-07 和 STAR-08 只有在存在真实事件时才作为行为题使用。
