# 高级前端开发工程师面试指导

版本：2026-07-15  
候选人定位：高级前端开发工程师（核心） / Web3 Frontend Engineer（差异化优势）  
目标工作方式：成都现场或国内远程

## 使用说明

这不是逐字背诵稿。先记住结论和证据，再用自己的语言表达。推荐按以下顺序复习：

- `P0`：必须掌握。简历上直接写到、面试官高概率追问，或一旦答错会损害可信度。
- `P1`：高优先级。Senior Frontend 常见深挖题，应能在 2 分钟内给出结构化回答。
- `P2`：补充。用于扩展深度，不必主动展开。

题型分为：`基础确认题`、`Senior 深挖题`、`项目追问题`、`压力题`。项目回答优先采用“背景 - 决策 - 权衡 - 结果”结构。没有公开数据时，讲责任边界、技术复杂度、交付结果和可验证产物，不编造用户量、交易量、转化率或性能提升比例。

### 回答长度

- 30 秒：只说结论、角色和最强证据。
- 90 秒：补背景、关键决策和结果。
- 3 分钟：再补取舍、失败路径、监控和复盘。

### 事实标签

- `已确认`：可按本文口径直接讲。
- `原理题`：是技术知识，不代表项目一定使用过。
- `需个人化`：本文只给安全结构，必须替换成本人真实事件，不能把模板当经历。

### Q07 [P0][压力题][已确认] 讲一次失败或线上问题

**面试官问**

讲一个你做得不够好的案例，以及怎么复盘。

**参考回答**

我会讲 Mint Forest 的大整数精度问题。链上数量通常以最小单位整数返回，范围可能超过 JavaScript `Number` 的安全整数；如果中间为了格式化直接转成 `Number`，即使页面看起来正常，实际比较、加减或提交参数都可能已经丢精度。

这件事的复盘重点不是“换一个库”就结束，而是明确数值边界：链上原始值在数据层保持 `bigint` 或十进制字符串；涉及小数展示时使用精度库或基于 decimals 的字符串格式化；只在确认范围安全的 UI 比例、像素和计数中使用 `number`。同时给公共格式化和合约参数转换补边界测试，Code Review 里把隐式 `Number(...)` 作为风险点。这个案例说明我后来更重视类型和数据边界，而不是只修当前页面。

**可能追问**

- 为什么 `BigInt` 不能解决所有小数问题？
- JSON 如何传 `bigint`？

**回答要点**

- `Number.MAX_SAFE_INTEGER` 是 `2^53 - 1`；超过后整数比较也可能错误。
- `BigInt` 适合整数原始单位，不能直接表达小数，也不能和 `number` 混算。
- JSON 原生不支持 `bigint`，跨边界通常转十进制字符串。

## 二、React

### Q11 [P0][基础确认题][原理题] React 从状态更新到页面变化经历什么

**面试官问**

React 的 render 和 commit 分别做什么？

**参考回答**

一次更新可以分为触发、render、commit。render 阶段执行组件并计算下一棵 React element / Fiber 结构，判断需要发生哪些变化；这个阶段应该是纯计算，不能依赖副作用。commit 阶段把变化应用到 DOM，并处理 ref、layout effect 等与真实宿主环境相关的工作。之后浏览器才进行 layout 和 paint，普通 `useEffect` 通常在绘制后执行。

Senior 回答要强调：组件函数重新执行不等于 DOM 一定变化；React 先计算差异，commit 只做必要更新。性能优化不能只数 render 次数，还要看 render 成本、commit 成本和浏览器绘制。

### Q12 [P0][Senior 深挖题][原理题] reconciliation、key 和 Fiber 是什么关系

**面试官问**

请解释 reconciliation 和 Fiber，为什么列表必须有稳定 key？

**参考回答**

reconciliation 是 React 根据前后两次 element 结构决定保留、更新还是卸载哪些节点的过程。Fiber 是 React 内部表示工作单元和组件树的实现结构，使 render 工作可以被分片、标记优先级并在需要时重做；它不是浏览器线程，也不是公开 API。

列表比较时，`key` 用来表达同级节点的稳定身份。稳定 key 能让 React 正确保留组件状态并移动节点；用数组下标作为 key，在插入、删除或排序时可能把旧状态错误地复用到另一个项目。key 只需在同级列表内唯一，但必须与业务实体稳定对应。

**容易踩坑**

- 说 Virtual DOM 比 DOM “一定更快”。
- 说 Fiber 创建了多线程。
- 说 key 会作为普通 prop 自动传给组件。

### Q13 [P0][基础确认题][原理题] 为什么 state 像快照

**面试官问**

连续调用三次 `setCount(count + 1)` 为什么不一定加三？

**参考回答**

一次 render 里的 `count` 是那次 render 的快照，事件处理函数闭包捕获的也是这个值。三次 `setCount(count + 1)` 都在请求设置同一个结果。需要基于前一次更新计算时，应写成 `setCount(c => c + 1)`。React 还会批量处理同一事件中的更新，减少不必要 render。

这也解释了为什么异步回调会出现 stale closure：回调读取的是创建时那次 render 的值。解决方式取决于需求，可以用函数式更新、正确依赖、ref 保存最新可变值，或重新设计状态归属，而不是随意关闭 lint 规则。

### Q14 [P0][Senior 深挖题][原理题] Hooks 为什么不能写在条件分支里

**面试官问**

Hooks 的规则是什么，背后的原因是什么？

**参考回答**

Hook 要在 React 组件或自定义 Hook 顶层调用，不能放进条件、循环或普通函数。核心原因是 React 依赖稳定的调用顺序把每次 render 的 Hook 状态对应起来；如果某次 render 少调用一个 Hook，后续状态槽位就会错位。

如果业务确实有条件，应保持 Hook 调用稳定，把条件放到 Hook 内部或返回值处理里；如果条件代表完全不同的组件状态，拆成不同组件通常更清晰。

### Q15 [P0][Senior 深挖题][原理题] `useEffect` 最常见的问题是什么

**面试官问**

你怎么理解 `useEffect`，如何避免依赖和竞态问题？

**参考回答**

`useEffect` 用来把 React 状态与外部系统同步，例如订阅、定时器、网络连接或非 React widget，不是通用的数据流工具。能在 render 中计算的派生值不要放 effect；由用户事件触发的动作优先放事件处理函数。

依赖要包含 effect 读取的响应式值。异步请求要处理过期响应：可以用 `AbortController`、请求序号或数据请求库，确保旧请求不会覆盖新状态。清理函数要撤销订阅、定时器和外部资源。Strict Mode 开发环境的额外执行用于暴露不对称的 setup / cleanup，不应该靠全局标志绕过。

### Q16 [P0][Senior 深挖题][原理题] Context 和 Zustand 怎么选

**面试官问**

什么时候用 Context，什么时候用 Zustand？

**参考回答**

Context 更适合低频、树级别依赖，例如主题、语言、认证上下文或注入服务。它解决的是跨层传递，不自动提供细粒度订阅；Provider 的 value identity 变化会让读取该 Context 的消费者重新 render。

Zustand 更适合多个远距离组件共享、更新频繁且需要 selector 的客户端状态。Mint Forest 的页面状态、用户信息和选中 Forest 等跨区域状态适合 store；Canvas 内每帧变化的位移、速度则不应该全进全局 store，而应放 ref 或渲染引擎对象，避免 React 每帧 render。选择依据是状态生命周期、更新频率、订阅粒度和可测试性，不是“项目大就上状态库”。

### Q17 [P0][基础确认题][原理题] `memo`、`useMemo`、`useCallback` 有什么区别

**面试官问**

这三个 API 应该怎么用？

**参考回答**

`memo` 缓存组件在 props 相同情况下的渲染结果；`useMemo` 缓存计算结果；`useCallback` 缓存函数引用。它们都是性能优化，不是正确性保证。只有当计算或子组件确实昂贵、引用稳定能阻止下游工作，并且 Profiler 证明收益时才使用。

滥用会增加依赖维护和比较成本，还可能因为对象、数组或函数每次重新创建导致缓存失效。先减少不必要的状态提升、拆分组件、让 props 更稳定，再考虑 memoization。

### Q18 [P1][Senior 深挖题][原理题] React 并发特性解决什么问题

**面试官问**

`startTransition`、`useTransition` 和 `useDeferredValue` 有什么用？

**参考回答**

它们不是让 JavaScript 多线程执行，而是让 React 区分紧急和非紧急更新。输入框回显属于紧急更新；大列表筛选、图表或路由内容切换可以标成 transition，让 React 在更高优先级更新到来时中断或重做非紧急 render。`useDeferredValue` 适合让某个值的下游渲染延后。

这些 API 不能消除真正阻塞主线程的重计算；如果一次 JavaScript 任务本身很长，还要拆任务、优化算法或移到 Worker。当前已确认项目事实不包含大规模使用 React 并发特性，面试时应讲原理和适用边界，不包装成业绩。

### Q19 [P1][Senior 深挖题][原理题] Suspense 是什么，不是什么

**面试官问**

你怎么理解 Suspense？

**参考回答**

Suspense 是声明式等待边界：当其子树使用受支持的方式挂起时，React 显示 fallback，数据或代码准备好后再恢复内容。常见场景包括 `lazy` 代码加载、框架集成的数据读取和流式服务端渲染。

它不是给任意 `useEffect + fetch` 自动加 loading，也不是错误处理方案；加载失败仍需要 Error Boundary 或框架错误边界。边界粒度应与用户感知一致，避免整个页面因为一个小模块退回全屏 loading。

### Q20 [P1][Senior 深挖题][原理题] Error Boundary 能捕获哪些错误

**面试官问**

错误边界怎么设计？

**参考回答**

传统 Error Boundary 捕获子树 render、生命周期和构造过程中的错误，并显示降级 UI；它通常不能自动捕获事件处理器、普通异步回调、服务端渲染或错误边界自身的错误。事件和异步流程仍要显式 `try/catch`、Promise 错误处理和状态反馈。

设计上我会按产品恢复能力划分边界：页面级边界避免白屏，复杂独立模块可以有局部边界；同时记录版本、路由、用户操作上下文和错误堆栈。不能只展示“出错了”，还要提供重试、返回或刷新路径。

### Q21 [P1][Senior 深挖题][原理题] 如何设计可维护的 React 组件

**面试官问**

你判断一个组件是否需要拆分的标准是什么？

**参考回答**

我不按行数机械拆分，主要看职责和变化原因。UI 展示、业务状态、数据获取、外部副作用和底层交互如果因不同原因变化，应分开。组件 API 应表达业务意图，避免几十个布尔 prop；复杂互斥状态用 discriminated union 或显式状态机更可靠。

Mint Forest 的做法可以用来说明边界：地图渲染、手势事件、业务建筑层和全局页面状态是不同职责；每帧位置放在 ref / Two.js 对象中，React 只承载需要声明式更新的 UI。这样既避免高频 render，也便于分别测试。

### Q22 [P1][项目追问题][已确认] Mint Forest 为什么选择 Canvas 与 DOM 混合

**面试官问**

为什么地图不用纯 DOM，为什么又没有全部画进 Canvas？

**参考回答**

地图背景、精灵和连续位移适合 Canvas：对象多、更新频率高，用 Two.js 统一坐标和每帧渲染更直接。菜单、弹窗、建筑交互和文本适合 DOM：可访问性、响应式布局、事件和业务组件维护成本更低。

混合方案的难点是坐标同步。我的实现把 Canvas group 的平移和缩放作为主变换，再把同样的变换同步到 DOM 地图元素层；缩放、聚焦和边界约束都走统一计算。取舍是同步逻辑更复杂，但比全 DOM 的高频 style 更新或全 Canvas 的 UI 可维护性问题更可控。

### Q23 [P1][项目追问题][已确认] 如何实现地图拖动、缩放和惯性

**面试官问**

Mint Forest 地图交互的核心实现是什么？

**参考回答**

拖动时记录上一帧指针位置和时间，计算位移增量并更新 group translation，同时把速度归一到帧尺度。释放后用 `requestAnimationFrame` 驱动惯性，速度每帧乘衰减系数，低于阈值停止。缩放会限制在根据容器和地图尺寸计算出的最小比例与最大比例之间，并用 easing 从当前值过渡到目标值。

边界不是固定常量，而是根据缩放后的图片尺寸和容器尺寸计算 `min/max`，每次平移、缩放和 resize 后重新 clamp。触摸端通过 `@use-gesture/react` 处理单指拖动和 pinch，滚轮还要过滤触控板惯性噪声。高频状态放 ref，不进入 React state。

### Q24 [P1][Senior 深挖题][原理题] React 性能问题怎么定位

**面试官问**

页面卡顿，你如何判断是不是 React 的问题？

**参考回答**

先复现并分类：加载慢、交互延迟、滚动掉帧还是内存增长。Chrome Performance 看主线程长任务、layout、paint 和脚本调用；React DevTools Profiler 看哪些组件 render / commit 花时和为什么更新。两者要结合，因为 React render 快不代表图片解码、Canvas 绘制或布局不慢。

优化顺序是先找到最高成本，再减少工作：缩小状态影响范围、避免无意义 effect、稳定 props、虚拟化列表、拆分长任务、降低 Canvas 每帧对象创建。最后用同一设备和同一操作复测，不用主观“感觉更快”验收。

### Q25 [P2][Senior 深挖题][原理题] 受控组件与非受控组件怎么选

**面试官问**

表单一定要做成受控组件吗？

**参考回答**

不是。受控组件把值放在 React state，适合实时校验、联动和统一状态；非受控组件让 DOM 保存当前值，通过 ref 或表单提交读取，适合简单输入或降低每次输入的 render 成本。选择取决于是否需要即时业务逻辑和状态一致性。

复杂表单还可以用表单库按字段订阅，不必把所有输入都提升到页面顶层。关键是提交时的数据真相唯一、校验和错误定位清楚。

### Q26 [P2][Senior 深挖题][原理题] 如何避免 Context 导致整棵树更新

**面试官问**

Context 性能不好怎么办？

**参考回答**

先确认是否真的存在性能问题。常见措施是拆分不同变化频率的 Context，稳定 Provider value，缩小 Provider 范围，把高频可选择状态移到支持 selector 的 store。不要用一个大对象同时承载主题、用户、列表和动画状态。

如果消费者自身昂贵，可以拆出读取 Context 的薄组件，再把稳定 props 传给 memoized 子组件。最终仍应以 Profiler 证据判断，而不是看到 Context 就替换。

## 三、Next.js

### Q27 [P0][基础确认题][原理题] Pages Router 和 App Router 的核心区别

**面试官问**

你如何比较 Pages Router 和 App Router？

**参考回答**

Pages Router 以 `pages` 文件系统路由为核心，页面数据常通过 `getStaticProps`、`getServerSideProps`、`getStaticPaths` 或客户端请求获取，成熟、直观，适合已有项目维护。App Router 建立在 React Server Components 之上，提供嵌套 layout、Server / Client Component 边界、流式渲染、Route Handler 和更细的缓存能力。

两者不是简单的新旧替换。App Router 能减少客户端 JavaScript、改善数据与 UI 共置，但会增加服务端边界、缓存和序列化的认知成本。Mint Forest 已确认的实际项目经验以 Pages Router 为主；面试时可以说明 App Router 的设计和迁移判断，但不要声称已在该项目完成大规模迁移。

### Q28 [P0][Senior 深挖题][原理题] Server Component 和 Client Component 怎么划边界

**面试官问**

App Router 中哪些组件应该写 `use client`？

**参考回答**

Server Component 适合数据访问、读取服务端资源、组合静态内容和减少客户端 bundle；它不能使用客户端 state、effect、事件处理器或浏览器 API。Client Component 用于交互、状态、effect、钱包 SDK、Canvas、手势和浏览器能力。

`use client` 声明的是客户端模块图入口，不是“这个文件只在浏览器生成 HTML”。边界应尽量下沉到真正需要交互的叶子，把数据和静态布局保留在服务端；传给 Client Component 的 props 需要可序列化。Mint Forest 的钱包、Canvas 和手势部分天然是 client boundary，营销和静态介绍页则可以更多留在服务端。

### Q29 [P0][Senior 深挖题][原理题] hydration 是什么，为什么会 mismatch

**面试官问**

如何定位 hydration mismatch？

**参考回答**

hydration 是 React 在服务端生成的 HTML 上绑定客户端组件逻辑和事件，使其可交互。首个客户端 render 应与服务端输出一致；如果 render 中直接读取 `window`、当前时间、随机数、localStorage、浏览器尺寸，或服务端和客户端拿到不同数据，就可能 mismatch。

定位时先比较服务端 HTML 和客户端首帧数据，找非确定性分支。解决方式不是统一加 `suppressHydrationWarning`，而是让首帧确定：浏览器专属值放 effect 后读取，必要时给稳定占位；纯客户端重组件可动态加载并明确关闭 SSR；数据要使用同一快照。`suppressHydrationWarning` 只适合确实不可避免的局部文本。

### Q30 [P0][基础确认题][原理题] SSR、SSG、ISR、CSR 怎么选

**面试官问**

请解释几种渲染方式和 trade-off。

**参考回答**

SSG 在构建时生成 HTML，适合内容稳定、可提前生成的页面，CDN 命中和首屏性能好，但更新需要重新构建。ISR 在静态生成基础上按时间或按需重新验证，适合可接受短暂陈旧的内容。SSR 每次请求生成页面，适合个性化、权限或必须读取请求时数据的场景，但服务端成本和延迟更高。CSR 先加载壳和 JavaScript，再在浏览器取数，适合登录后强交互区域，但首屏和 SEO 通常更弱。

实际项目可以混合选择。作品集和官网优先 SSG；用户私有资产或权限页面可能 SSR / server rendering；实时交易状态更适合客户端订阅或轮询。选择依据是新鲜度、个性化、SEO、缓存、成本和失败模式，不是固定使用一种。

### Q31 [P0][Senior 深挖题][原理题] Pages Router 的数据获取边界

**面试官问**

`getStaticProps` 和 `getServerSideProps` 的区别是什么？

**参考回答**

`getStaticProps` 在构建时执行，也可配合 `revalidate` 做 ISR；返回数据用于预渲染，适合可缓存内容。动态路径通常配合 `getStaticPaths`。`getServerSideProps` 在每次请求时运行，可读取请求相关信息，适合个性化或必须实时生成的页面。

两者都只从 page 导出，返回 props 会进入客户端可见的页面数据，所以不能把 secret 放进去。`getServerSideProps` 内可以直接访问后端资源，不需要为了调用自己再绕一层 API Route。客户端实时数据则应独立管理缓存、取消和错误状态。

### Q32 [P0][Senior 深挖题][原理题] App Router 的 cache 容易错在哪里

**面试官问**

Next.js 的缓存和 revalidation 怎么理解？

**参考回答**

我会先区分被缓存的是什么：数据请求或函数结果、预渲染输出，以及客户端路由访问过的结果，它们的生命周期和失效方式不同。App Router 版本间缓存默认值有变化，不能背一句“fetch 默认永久缓存”就套所有版本。

设计时明确每份数据的新鲜度和失效事件：公开且稳定的数据可缓存；用户私有或请求相关数据不应跨用户复用；内容发布后可以按 path 或 tag 失效。排查时记录请求是否命中缓存、cache key 包含什么、哪个部署版本产生，以及 revalidation 是时间触发还是业务事件触发。

**容易踩坑**

- 把浏览器 HTTP cache、CDN cache、Next data cache 和 React memoization 混成一个概念。
- 忽略用户身份导致数据串用。
- 不确认 Next.js 具体版本就背默认行为。

### Q33 [P1][基础确认题][原理题] Next.js 动态路由和浅路由

**面试官问**

Pages Router 的动态路由怎么设计？

**参考回答**

文件名 `[id].tsx` 表示动态段，`[...slug]` 是 catch-all，`[[...slug]]` 是 optional catch-all。读取参数时要注意自动静态优化页面的 `router.query` 首次可能还没准备好，不能把 `undefined` 当业务错误。

浅路由只更新当前页面的 URL 和 router state，不重新运行页面级数据获取，适合筛选、tab 等当前页面状态；跨页面或依赖服务端重新取数时不应使用。路由参数应验证和规范化，不能直接作为可信 API 参数。

### Q34 [P1][Senior 深挖题][原理题] Middleware 适合做什么

**面试官问**

你会把鉴权都写进 Middleware 吗？

**参考回答**

Middleware 适合在请求进入路由前做轻量重写、重定向、locale、实验分流或粗粒度访问判断。它不是完整业务授权层，也不适合重数据库查询和复杂计算；真正的资源权限必须在服务端数据或 API 边界再次校验。

我会先确认 runtime、依赖兼容和 matcher 范围，避免静态资源也执行。身份信息只用于做初步导航，不能因为前端或 Middleware 隐藏入口就认为数据安全。

### Q35 [P1][Senior 深挖题][原理题] loading、error 和 not-found 如何设计

**面试官问**

App Router 的错误和加载边界怎么划分？

**参考回答**

边界应与可独立恢复的产品区域一致。`loading` / Suspense fallback 负责等待体验；`error` 边界负责该 route segment 的运行错误和重试；`not-found` 表达资源确实不存在。不要把网络超时、权限不足和不存在全部显示成 404。

页面级错误要保留导航和恢复路径，局部模块失败不应拖垮整个页面。日志需要带 route、deployment、request id 和业务动作，用户界面只显示可理解的信息，不直接暴露内部错误栈。

### Q36 [P1][Senior 深挖题][原理题] 如何避免服务端数据瀑布

**面试官问**

Server Component 中多个请求如何优化？

**参考回答**

先看依赖关系。互不依赖的请求应尽早启动并用 `Promise.all` 并行；有真实依赖的请求保持顺序。组件树可以通过 Suspense 边界流式输出，不让慢模块阻塞整个页面。重复读取同一资源时再考虑请求去重或缓存。

但并行不是越多越好，还要考虑后端容量、连接数和失败聚合。性能分析要看服务端 trace 和实际 TTFB / stream timing，不只看前端 waterfall。

### Q37 [P1][项目追问题][已确认] Mint Forest 为什么适合 client-heavy 架构

**面试官问**

Mint Forest 为什么不做成主要依赖 Server Component 的页面？

**参考回答**

它的核心价值是登录后的 Canvas 地图、拖动、pinch、动画、钱包和合约交互，这些都依赖浏览器状态与即时事件，天然是 client-heavy。服务端渲染可以优化入口壳、SEO 信息和静态配置，但无法替代持续的客户端交互。

我会把静态内容、首屏骨架和可缓存配置与运行时交互分开；地图引擎和钱包 provider 只在需要的路由加载，避免污染全站 `_app` 或根 layout。当前作品集迁移后的薄路由和项目 ownership 也体现了这种隔离思路，但不能把后来的本地化改造说成原生产项目架构成果。

### Q38 [P2][Senior 深挖题][原理题] 什么时候值得从 Pages Router 迁移到 App Router

**面试官问**

你会主动推动老项目迁 App Router 吗？

**参考回答**

不会为了“新”整体重写。先看收益是否明确：是否能减少客户端 bundle、改善嵌套 layout、流式数据加载或服务端数据访问；再评估钱包 SDK、状态库、第三方组件、缓存语义和团队经验。可以从低耦合新路由或静态页面渐进迁移，并建立 hydration、缓存和 E2E 基线。

如果核心页面高度 client-heavy、现有 Pages Router 稳定，迁移收益可能有限。Senior 的判断是控制迁移风险和业务价值，不是追版本。

## 四、前端性能与体验

### Q39 [P0][基础确认题][原理题] Core Web Vitals 是什么

**面试官问**

LCP、INP、CLS 分别衡量什么？

**参考回答**

LCP 衡量主要内容的加载速度；INP 衡量一次页面访问中用户交互的总体响应性；CLS 衡量意外布局偏移。当前“good”参考阈值是 LCP 不超过 2.5 秒、INP 不超过 200 毫秒、CLS 不超过 0.1，并以真实用户访问的第 75 百分位判断。

实验室数据适合复现和调试，真实用户监控反映设备、网络和地区分布。项目优化要先按页面类型和设备分组，不用平均值掩盖低端移动端问题，也不能只跑一次 Lighthouse 就声称线上达标。

### Q40 [P0][Senior 深挖题][原理题] LCP 慢怎么排查

**面试官问**

首页 LCP 很差，你从哪里开始？

**参考回答**

先确认 LCP 元素是什么，再把时间拆成 TTFB、资源发现、下载和渲染延迟。若是 hero 图片，检查尺寸、格式、响应式 `srcset`、优先级、CDN 缓存和是否被 JavaScript 延迟发现；若是文本，检查字体阻塞和服务端输出；若 TTFB 高，查服务端数据瀑布和缓存。

优化后用真实页面和目标移动设备复测，防止把 LCP 元素换小但真实内容更晚出现。没有量化前后数据时，只能描述优化方法，不能编造提升百分比。

### Q41 [P0][Senior 深挖题][原理题] INP 差和长任务有什么关系

**面试官问**

点击后页面 500ms 才响应，你怎么查？

**参考回答**

INP 包含输入延迟、事件处理时间和下一次绘制前的呈现延迟。先用 Performance trace 找交互发生时的长任务，拆开 JavaScript、style/layout、paint。常见问题包括一次同步处理大量数据、级联 render、第三方脚本、强制同步布局和 Canvas 每帧工作过多。

处理方式是减少或拆分主线程工作：只更新必要状态、虚拟化、把重计算放 Worker、用 scheduler / yielding 分块、避免读写布局交错。transition 只能调整 React 更新优先级，不能让一个 300ms 的纯 JavaScript 函数自动变快。

### Q42 [P1][基础确认题][原理题] CLS 怎么治理

**面试官问**

页面布局抖动常见原因是什么？

**参考回答**

图片、视频、广告或异步模块没有预留尺寸，字体替换改变字形尺寸，或在已有内容上方插入 UI，都会产生 CLS。治理时为媒体声明宽高或 `aspect-ratio`，为异步区域预留稳定骨架，选择合适字体 fallback 和加载策略，动画优先使用 transform / opacity。

还要区分用户操作后预期发生的布局变化与意外偏移，并用 field data 定位真实页面和设备。

### Q43 [P0][Senior 深挖题][原理题] bundle 过大怎么处理

**面试官问**

你如何分析和减少前端 bundle？

**参考回答**

先用构建分析器看入口、重复依赖和最大模块，再结合 coverage 看下载后是否实际执行。优化优先级通常是删除不需要的依赖、改成更小的导入路径、路由和组件级 code splitting、动态加载重型编辑器/图表/钱包/Canvas，以及避免 server-only 代码进入 client graph。

不能只追总 bundle 数字，要看首屏关键 chunk、缓存复用和交互时二次加载。Mint Forest 的 Two.js、地图资源和钱包能力只应在对应路由加载，不该放进作品集全局入口。

### Q44 [P0][项目追问题][已确认] Canvas 地图如何做性能控制

**面试官问**

Mint Forest 地图对象和动画多，如何保持流畅？

**参考回答**

第一，高频位移、速度和缩放保存在 ref 和 Two.js group 中，不让每一帧触发 React state。第二，动画统一走 `requestAnimationFrame`，惯性低于阈值停止，避免多个独立 timer。第三，地图背景和精灵资源先加载，Canvas 根据 `devicePixelRatio` 和容器 resize 更新尺寸。

还要控制每帧对象创建、可见对象数量和 DOM / Canvas 同步次数。性能验证看帧时间、长任务和低端移动端触摸，不只在开发机上拖动几次。当前源码能证明实现了这些机制，但没有已确认的 FPS 提升数字，所以不报虚构指标。

### Q45 [P1][Senior 深挖题][原理题] 大列表怎么优化

**面试官问**

一万条数据列表如何渲染？

**参考回答**

优先确认产品是否真要同时展示一万条。常见方案是分页或增量加载；确需连续滚动时用虚拟列表，只渲染视口附近元素。固定高度最简单，动态高度需要测量和缓存，还要处理滚动定位、可访问性和搜索。

数据计算可用 memoization，但不能替代虚拟化。行组件保持稳定 key 和小 props，避免父级高频状态让所有行重 render。最终以滚动帧率、内存和交互响应验证。

### Q46 [P1][基础确认题][原理题] 图片和字体怎么优化

**面试官问**

除了压缩图片，还有什么？

**参考回答**

图片要按显示尺寸输出，使用现代格式、响应式候选、合理 lazy loading，并为 LCP 图片设置更高优先级而不是懒加载。声明尺寸避免 CLS，静态资源使用内容 hash 和长期缓存。字体要减少字重和字符集，合理 preload，使用合适 `font-display`，并配置尺寸接近的 fallback。

Next Image 和 Font 能提供默认优化，但仍要正确标注尺寸、priority 和使用范围，工具不会替代资源策略。

### Q47 [P1][Senior 深挖题][原理题] 浏览器缓存和 CDN 缓存怎么设计

**面试官问**

静态资源与接口的缓存策略有什么不同？

**参考回答**

带内容 hash 的静态资源可以 `max-age` 很长并标记 immutable，因为 URL 随内容变化。HTML 通常需要短缓存或 revalidation，避免引用旧构建资源。公开 GET API 可以按业务新鲜度使用 CDN cache、`s-maxage` 和 `stale-while-revalidate`；用户私有数据必须正确设置 private / no-store，并确保 cache key 包含必要身份维度。

发布时还要考虑版本偏斜：旧页面引用的新旧 chunk、前端和 API schema 不一致。缓存不是单点配置，而是浏览器、CDN、框架和业务失效事件的整体设计。

### Q48 [P1][项目追问题][已确认] 如何做移动端适配

**面试官问**

Mint Forest 的移动端适配难点是什么？

**参考回答**

它不是把桌面布局缩小。核心难点是触摸输入、双指缩放、惯性、浏览器 viewport、横竖屏和性能。交互上区分单指拖动与 pinch，阻止浏览器原生 gesture 与页面缩放冲突；菜单和弹窗按移动端信息层级重新布局；地图最小缩放根据容器尺寸动态计算。

验证要覆盖真实 viewport、触摸手势、低端设备和主流移动浏览器。当前项目还有 desktop / mobile Playwright 覆盖，可作为工程方法证据，但不要把作品集迁移后的测试全部说成 2025 年生产版本原有成果。

## 五、JavaScript 与 TypeScript

### Q49 [P0][基础确认题][原理题] 事件循环输出题怎么回答

**面试官问**

Promise、`setTimeout` 和同步代码的执行顺序是什么？

**参考回答**

当前 task 的同步代码先运行到栈清空；随后清空 microtask queue，Promise reaction 和 `queueMicrotask` 在这里执行；浏览器再有机会渲染，然后进入后续 task，例如 timer 或事件。每个 task 结束后都会继续清空 microtask，microtask 还可以追加 microtask，所以滥用会推迟渲染和 timer。

回答具体题时逐行标出“同步执行、注册回调、Promise resolve、microtask、task”，不要只背“Promise 比 setTimeout 快”。

### Q50 [P0][Senior 深挖题][原理题] Promise 错误和并发怎么处理

**面试官问**

`Promise.all`、`allSettled`、`race`、`any` 怎么选？

**参考回答**

`all` 适合全部成功才有意义的并行任务，任一 reject 就让聚合 Promise reject，但其他任务不会自动取消。`allSettled` 适合批量任务需要收集每项结果。`race` 返回最先 settled 的结果，常用于超时竞争，但还要主动取消原任务。`any` 返回第一个 fulfilled，全部失败才抛 `AggregateError`。

项目里还要限制并发度、传递 `AbortSignal`、设置超时和幂等重试。多链批量操作不能只用一个 `Promise.all`，因为钱包签名通常需要串行或受能力约束，链上结果也要按单项状态聚合。

### Q51 [P0][基础确认题][原理题] 闭包是什么，React 中有什么风险

**面试官问**

请解释闭包和 stale closure。

**参考回答**

闭包是函数与其创建时词法环境的组合，让函数在外层执行结束后仍能访问相关变量。它是模块封装、回调和 Hook 的基础。风险是异步回调或 effect 可能捕获旧 render 的 state / props，造成 stale closure。

解决时先确认语义：基于前值更新用函数式 setState；订阅回调需要最新值可用 ref；effect 依赖必须完整；如果回调应该随值更新，就让它重新创建。不要用空依赖和 lint disable 隐藏问题。

### Q52 [P1][基础确认题][原理题] 原型链和 class 的关系

**面试官问**

JavaScript 的继承是怎么实现的？

**参考回答**

对象读取属性时先查自身，没有再沿 `[[Prototype]]` 链查找。构造函数的 `prototype` 是通过 `new` 创建实例时使用的原型对象；`class` 提供更清晰的语法和语义约束，但底层仍基于原型机制。

`hasOwn` 用于判断自身属性，`in` 会沿原型链。修改内建原型会污染全局行为，业务代码一般避免。面试回答要区分构造函数本身的 prototype 属性和实例的内部原型。

### Q53 [P0][项目追问题][已确认] JavaScript 大整数为什么会丢精度

**面试官问**

链上金额为什么不能直接转 `Number`？

**参考回答**

JavaScript `number` 使用 IEEE 754 双精度浮点，安全整数上限是 `2^53 - 1`。链上 token amount 常以整数最小单位表示，例如带 18 decimals 的数量很容易超过这个范围，转 `Number` 后可能出现两个不同整数比较相等、加减或格式化错误。

我的原则是 raw amount 在 API、store 和合约参数边界保持字符串或 `bigint`；计算显示值时按 decimals 做精确转换，涉及小数用十进制精度库；只在确认安全的比例或 UI 数值中使用 `number`。序列化前把 `bigint` 显式转字符串。

### Q54 [P0][基础确认题][原理题] TypeScript 类型收窄有哪些方式

**面试官问**

如何从 `unknown` 安全得到业务类型？

**参考回答**

可以使用 `typeof`、`instanceof`、`in`、判等、控制流和自定义 type predicate 收窄。外部数据先视为 `unknown`，经过 runtime validation 后再进入领域类型；`as` 只是告诉编译器相信开发者，不会做运行时校验。

复杂状态建议使用 discriminated union，例如交易状态用 `status` 区分 `idle / signing / submitted / confirmed / failed`，每个分支只暴露合法字段，配合 `never` 做穷尽检查。

### Q55 [P0][Senior 深挖题][原理题] 泛型应该解决什么问题

**面试官问**

你如何设计一个类型安全的请求函数？

**参考回答**

泛型用于保留输入和输出之间的关系，不是为了把所有类型写成 `<T>`。请求层可以让调用方声明响应类型，但仅有 `request<T>()` 仍不能证明服务端数据真实符合 T；边界还需要 schema 校验或明确 decoder。

设计时用约束表达能力，例如 `K extends keyof T`；避免无意义泛型、过度条件类型和大量断言。对 SDK 而言，稳定、可理解的公开类型比炫技更重要，破坏性类型变更也要按版本管理。

### Q56 [P1][Senior 深挖题][原理题] `any`、`unknown`、`never` 怎么用

**面试官问**

三者有什么区别？

**参考回答**

`any` 基本关闭类型检查，适合受控迁移或第三方缺失类型的窄边界，不应扩散。`unknown` 表示值未知，使用前必须收窄，适合 API、错误和消息边界。`never` 表示不可能出现的值或不返回，可用于 union 的穷尽检查。

错误处理里 `catch` 的值应当作 `unknown`，先判断是否为标准 Error、钱包 RPC error 或业务 error，再归一化；直接 `error as any` 会把真实兼容问题推到运行时。

### Q57 [P1][Senior 深挖题][原理题] interface 和 type 怎么选

**面试官问**

`interface` 与 `type` 有什么区别？

**参考回答**

两者都能描述对象形状。interface 支持声明合并和 extends，适合需要扩展的公共对象契约；type 可以表达 union、tuple、映射类型和条件类型，更灵活。项目里我更关注一致性和语义：领域状态 union 用 type，公共可扩展对象可用 interface。

不要把选择上升为架构优劣。真正重要的是边界清楚、避免重复定义和保持公开 API 兼容。

### Q58 [P1][Senior 深挖题][原理题] 如何建立前后端类型边界

**面试官问**

有 TypeScript 以后为什么线上仍会有类型错误？

**参考回答**

TypeScript 只检查编译期代码，网络响应、localStorage、URL、钱包 provider 和第三方脚本都是运行时输入。需要在边界做 schema 校验、默认值和版本处理，校验通过后再转领域类型。

工程上可从 OpenAPI / schema 生成基础类型，但仍要处理后端兼容窗口、可选字段和业务语义。前端不能因为类型文件存在就假设线上响应永远正确。

### Q59 [P1][项目追问题][已确认] 多链业务的类型怎么设计

**面试官问**

EVM 和 Solana 差异很大，TypeScript 如何避免到处写判断？

**参考回答**

我会把上层业务定义成稳定领域模型，例如资产候选项、预校验结果、交易步骤和聚合状态；底层用 discriminated union 区分 `evm` 与 `solana`，各自携带合法字段。通过 adapter 暴露统一动作，如 `build / simulate / submit / queryStatus`，但不强行让底层交易对象同构。

这样共性在业务层复用，chain-specific 逻辑在适配器内收敛。需要 EVM `chainId` 的分支不会误拿 Solana `cluster`，需要 ATA / ALT 的字段也不会污染 EVM 类型。

### Q60 [P2][Senior 深挖题][原理题] 如何控制 TypeScript 工程复杂度

**面试官问**

类型太复杂影响开发效率怎么办？

**参考回答**

先检查类型是否在表达真实业务约束。如果一个类型需要多层条件类型才能理解，可能是公共模型承担了太多职责。可以拆领域类型、减少跨层复用、给复杂类型命名，并在边界用显式转换。

编译性能还要检查巨型 union、递归条件类型、重复生成类型和项目引用。类型系统目标是提前暴露错误、改善 API，而不是让开发者为了通过编译写更多断言。

### Q61 [P0][基础确认题][原理题] Webpack 和 Rollup 的差异

**面试官问**

Webpack 与 Rollup 怎么选？

**参考回答**

Webpack 更偏应用构建，loader / plugin 生态完整，能处理代码、样式、资源和复杂开发服务器；Rollup 的模块图和输出模型更适合 library，tree shaking 和多格式产物配置直观。现在很多框架会封装底层构建器，选择也受 Vite、Next.js 或现有基础设施约束。

NFTScan SDK 属于 library 场景，关注 ESM / CJS、类型声明、package exports、tree shaking 和发布内容；业务站点更关注路由分包、资源处理和开发体验。不能只用“Rollup 打包更小、Webpack 更强”一句话代替具体约束。

### Q62 [P1][Senior 深挖题][原理题] tree shaking 为什么会失效

**面试官问**

用了 ESM 为什么 bundle 还是很大？

**参考回答**

tree shaking 依赖静态模块结构和可判断的副作用。CommonJS 动态 `require`、顶层副作用、错误的 `sideEffects` 声明、把整个库聚合导入，都会影响删除未使用代码。即使模块被删除，重复版本、语言包和大资源仍可能占体积。

排查要看构建产物和模块图，确认是没有摇掉、重复打包还是确实被入口使用。`sideEffects: false` 不能随便加，否则 CSS 或注册逻辑可能被错误删除。

### Q63 [P0][Senior 深挖题][原理题] 你的测试策略是什么

**面试官问**

单元、集成和 E2E 怎么分工？

**参考回答**

单元测试覆盖纯规则、格式化、状态转换和边界条件，反馈快；集成测试验证组件、store、gateway 等协作；E2E 只覆盖高价值用户旅程、浏览器兼容和发布边界，不把所有组合都堆到浏览器层。

以 Mint Forest 这类项目为例，大整数转换、奖励重复领取和余额不足适合单元测试；登录、GreenID、Lucky Spin 和持久化适合集成 / E2E；网络边界可以在导航前监听请求，确保没有意外外部依赖。历史生产项目的具体覆盖率未确认，不报数字；当前作品集仓库已有 Vitest 和 desktop / mobile Playwright 证据，可说明我现在采用的验证方法。

### Q64 [P1][Senior 深挖题][原理题] 前端测试最容易写错什么

你怎么看快照测试和实现细节测试？

测试应验证用户可观察行为和稳定契约。大面积 DOM snapshot 容易在无意义结构变化时更新，真正回归反而被淹没；直接断言组件内部 state、私有方法或 class name 会绑死实现。

### Q65 [P0][项目追问题][已确认] NFTScan 发布脚本解决了什么

**面试官问**

你说发布操作从 4 步减少到 2 步，具体价值是什么？

当时多个前端项目的发布包含构建、产物修复、压缩、上传和远程部署，人工步骤多，容易漏步骤或上传错误产物。我把这些确定性操作收敛到发布脚本，覆盖 EVM、Solana、Aptos 和 TON 项目，使人工操作从约 4 步减少到 2 步。

### Q66 [P0][项目追问题][已确认] Vercel 多环境如何管理

**面试官问**

Mint Forest 的 Development、Preview、Production 如何避免混乱？

- 为什么本地正常 Preview 失败？

### Q67 [P0][Senior 深挖题][原理题] 如何设计前端监控

**面试官问**

前端监控应该采集什么？

我会分四层：可用性和 Core Web Vitals；JavaScript / resource / API 错误；关键业务漏斗和状态；发布版本、环境和用户上下文。Web3 还要记录 chain、wallet type、method、transaction hash 或 signature、阶段、标准化错误码和耗时，但避免上传敏感签名、token 或完整私有数据。

### Q68 [P0][Senior 深挖题][已确认] 线上故障怎么定位

**面试官问**

如果是生产事故，先止损：关闭入口、降级不稳定钱包、回滚或修正文案；同时保留 hash、request id 和 deployment id。恢复后复盘为什么 UI 没有超时、恢复或明确状态，并补监控和回归测试。

### Q70 [P1][Senior 深挖题][原理题] CI/CD pipeline 如何设计

### Q71 [P1][Senior 深挖题][原理题] 如何处理发布回滚

### Q73 [P0][基础确认题][已确认] EVM 和 Solana 前端的核心差异

**面试官问**

你同时做过 EVM 和 Solana，最大的差异是什么？

**参考回答**

EVM 常以账户、chainId、nonce、gas 和合约 ABI 为核心，钱包通常通过 EIP-1193 风格 provider 交互。Solana 交易由 instruction、显式 account 列表、recent blockhash 和签名组成，SPL Token 余额位于 Token Account，不是主钱包地址本身；复杂交易还要考虑 ATA、Legacy / V0 和 ALT。

前端层面不能只换 SDK。地址格式、单位、费用、交易构建、钱包能力、状态确认和错误恢复都不同。我会统一上层业务状态和交互语义，底层保留 chain adapter，不强行共用交易对象。

### Q74 [P0][基础确认题][已确认] wagmi 和 viem 分别负责什么

**面试官问**

为什么同时使用 wagmi 和 viem？

**参考回答**

viem 提供较底层、类型安全的 EVM 客户端能力，例如编码 ABI、读写合约、交易和 receipt；wagmi 在 React 层提供连接状态、账户、chain、hooks、缓存和 mutation 协调，并以 viem client 为基础。RainbowKit 主要解决钱包选择和连接 UI。

Mint Forest 中我用 RainbowKit、wagmi、viem 和 React Query 统一钱包与合约交互。统一不等于把错误抹平：业务层仍要区分拒签、链错误、余额不足、revert、RPC 超时和 receipt 失败。

### Q75 [P0][Senior 深挖题][已确认] 合约调用为什么要统一封装

**面试官问**

直接在组件里 `writeContract` 有什么问题？

**参考回答**

组件直接调用容易让 chain 检查、单位转换、参数编码、receipt 等待和错误翻译散落。Mint Forest 的旧实现把 GreenID、signin、invite、steal、turntable 和 reward 等写操作收敛到 service：统一把整数参数转为 `BigInt`，提交后等待 receipt，并把常见钱包 / 合约错误映射成用户可理解信息。

更完整的封装还应分 read、simulate、write、wait、normalize error，并把 transaction hash 和阶段回传 UI。组件负责展示和用户动作，service / hook 负责协议细节。取舍是封装不能吞掉原始错误和 chain-specific 信息，否则排障困难。

### Q76 [P0][Senior 深挖题][原理题] 一笔 EVM 交易有哪些状态

**面试官问**

前端 loading 应该如何建模？

**参考回答**

至少区分 preparing / simulating、awaiting signature、submitted、pending、confirmed success、reverted、rejected、replaced / dropped 和 unknown / timeout。用户拒签发生在钱包阶段，没有 hash；广播后有 hash，但 receipt 可能等待很久；receipt status 失败说明交易已上链但执行 reverted。

UI 要在刷新后根据 hash 恢复查询，超时只表示前端暂时不知道，不等于链上失败。重复点击要通过状态、幂等 key 或后端订单避免重复提交。

### Q77 [P0][Senior 深挖题][原理题] 合约错误怎么解析

**面试官问**

用户看到的错误信息从哪里来？

**参考回答**

我会按层解析：钱包标准错误码和拒签；RPC / transport 错误；simulation 或 estimate 错误；合约 revert reason / custom error；业务前置校验。展示层给可行动信息，例如切链、补 gas、检查余额或重试，同时日志保留原始错误、method、chain 和版本。

字符串 includes 映射可以作为兼容兜底，但长期更可靠的是按 error type、code 和 ABI custom error 解码。不能把所有异常都改成“网络错误”。

### Q78 [P0][项目追问题][已确认] EIP-5792 `wallet_sendCalls` 解决什么

**面试官问**

1DEX 为什么使用 `wallet_sendCalls`？

**参考回答**

EIP-5792 定义 Wallet Call API，`wallet_sendCalls` 让 DApp 请求钱包提交一批 `{to, data, value}` calls，并可通过能力和状态接口了解钱包支持与批次结果。Small Balance Convertor 或 Gas Top-up 这种多资产操作需要减少多次确认并聚合状态，因此会优先利用支持批量 calls 的钱包能力。

实现不能假设所有钱包都支持或保证原子性。先做 capability detection，校验 chain 和 from，处理用户拒绝、bundle 过大、unsupported capability，并准备单笔或钱包专用路径。批次返回 id 后还要查询 calls status，不是拿到 id 就算成功。

### Q79 [P0][项目追问题][已确认] EIP-7702 和 EIP-5792 有什么关系

**面试官问**

二者是否都是批量交易协议？

**参考回答**

不是同一层。EIP-7702 是新的交易类型和 authorization 机制，让 EOA 设置 delegation indicator，把执行委托给目标代码，从而获得更接近智能账户的能力。EIP-5792 是 DApp 与钱包之间的 JSON-RPC Wallet Call API，用于请求批量 calls、查询能力和状态。

钱包可能借助 7702 或其他账户机制实现 5792 的原子批量，但 DApp 不应假设实现细节。前端应以 `wallet_getCapabilities` 返回的能力为准，并明确 delegation 的持久性、nonce、授权、重放和恶意 delegate 风险。

### Q80 [P0][项目追问题][已确认] 为什么还要支持 OKX `executeFromSelf`

**面试官问**

有标准 API 后为什么写钱包专用逻辑？

**参考回答**

真实钱包能力和标准落地并不同步。1DEX 需要同时支持 MetaMask EIP-5792 路径和 OKX `executeFromSelf` 路径，不能用一个 method name 覆盖所有钱包。我的做法是先识别钱包和 capability，再进入对应 adapter；上层仍使用统一的批量操作状态和错误模型。

钱包专用 API 必须被隔离，避免散落在页面中；还要准备能力缺失时的清晰降级。不要说 `executeFromSelf` 是 EIP 标准，它是特定钱包能力。

### Q81 [P0][项目追问题][已确认] 最多 9 种 Token 怎么解释

**面试官问**

为什么单次最多操作 9 种 Token，是协议限制吗？

**参考回答**

这是项目的产品和工程上限，不应说成 EVM 或 Solana 协议固定只能 9 种。批量越大，calldata / instruction、账户数量、gas / fee、模拟失败概率、钱包展示和错误恢复都会更复杂；Solana 还受交易消息大小和 account 列表影响。

前端会在选择阶段限制数量，构建前再做余额、费用、ATA / account、钱包能力和交易大小预校验。如果面试官追问“9 的精确实验数据”，只能讲真实测试依据；当前确认的是实现支持最多 9 种，不编造阈值推导。

### Q82 [P0][基础确认题][已确认] Solana ATA 是什么

**面试官问**

为什么转 SPL Token 前可能要创建 ATA？

**参考回答**

SPL Token 不直接存放在用户的 System Account 中，而是在特定 mint 和 owner 对应的 Token Account。ATA 是按 wallet、Token Program 和 mint 确定性派生的标准账户地址，作为用户持有该 token 的主要账户约定。

转账前要派生并检查目标 ATA 是否存在；不存在时可把创建 ATA 的 instruction 与转账放进同一交易，payer 支付账户创建成本。还要区分 Token Program 与 Token-2022 的 program id，不能只按地址存在就假设 mint 和 owner 正确。

### Q83 [P0][Senior 深挖题][已确认] Legacy、V0 和 ALT 怎么选

**面试官问**

Solana Versioned Transaction 和 Address Lookup Table 解决什么？

**参考回答**

Legacy transaction 在 message 中直接列出账户地址，适合账户较少、钱包兼容路径简单的交易。V0 transaction 支持 Address Lookup Table，把常用 32-byte 地址通过表中索引引用，减少 message 里的地址体积，容纳更多账户。使用 ALT 加载地址必须走 v0 message。

1DEX 的多 Token 批量操作会根据 instruction 和账户数量选择 Legacy 或 V0，并获取需要的 ALT。前端还要确认钱包是否支持 versioned transaction、lookup table 是否存在和已激活、recent blockhash 是否有效。ALT 不是压缩所有交易数据，也不会减少指令本身的计算成本。

### Q84 [P0][Senior 深挖题][原理题] Solana 交易状态如何处理

**面试官问**

Solana signature 返回后就成功了吗？

**参考回答**

不是。钱包签名和 `sendTransaction` 返回 signature 只表示已签名并尝试提交。还要处理 simulation、RPC 发送错误、blockhash 过期、processed / confirmed / finalized 不同 commitment，以及链上 instruction error。

前端保存 signature、blockhash 和 last valid block height，按产品风险选择确认级别；超过有效高度应判断过期并决定重建，而不是无限轮询。批量操作需要按 transaction / token 聚合结果，部分成功时不能统一显示全部成功。

### Q85 [P0][Senior 深挖题][已确认] 多链批量操作如何设计状态机

**面试官问**

Small Balance Convertor 或 Gas Top-up 的前端状态怎么设计？

**参考回答**

我会把流程拆成 selection、prechecking、ready、awaiting wallet、submitted、confirming、partially succeeded、succeeded、failed / recoverable。每个资产还有独立状态和错误原因，上层聚合只负责用户理解，不能抹掉单项结果。

EVM adapter 处理 chain、allowance、calls、gas 和 receipt；Solana adapter 处理 ATA、instruction、Legacy / V0、ALT、blockhash 和 signature。订单 id 或 operation id 贯穿前端、钱包和后端状态，刷新后可以恢复。重试只重做可安全重试项，不重复已成功的链上动作。

### Q86 [P1][Senior 深挖题][原理题] 钱包签名登录怎么防重放

**面试官问**

### Q94 [P0][Senior 深挖题][已确认] Mint Forest 地图系统如何拆分

**面试官问**

请从系统设计角度解释 Canvas 地图。

**参考回答**

渲染层由 Two.js Canvas 负责地图纹理、鸟类 Sprite 和每帧更新；交互层由 gesture 容器统一 mouse、touch、pinch、wheel；变换层管理 scale、translation、velocity、bounds、focus 和 resize；DOM overlay 渲染建筑和业务组件；Zustand 管页面、用户和选中区域等低频业务状态。

拖动增量直接更新 group，速度进入 ref；释放后 rAF 惯性衰减；每次变换后按图片和容器尺寸 clamp，再同步到 DOM overlay。这样将高频图形状态与 React 业务状态分开。风险在于两层坐标漂移、resize、DPR 和资源加载顺序，需要统一变换函数和真实设备回归。

### Q99 [P1][Senior 深挖题][原理题] 设计一个多链资产页面

**面试官问**

如果重新设计 NFTScan Portfolio，你会考虑什么？

**参考回答**

先定义用户查询维度和一致性：地址可能属于不同 namespace，链上数据、索引服务和价格数据新鲜度不同。前端通过 chain registry 和 adapter 生成查询计划，并发受控请求；结果按 chain 独立展示 loading / error / stale 状态，再做可解释的聚合。

### Q100 [P0][Senior 深挖题][已确认] 设计一个统一交易状态系统

**面试官问**

如果多个产品都要做链上交易，如何抽公共能力？

**参考回答**

我会抽象“操作”而不是抽象所有链交易对象。公共模型包含 operation id、业务类型、chain、wallet、steps、hash / signature、状态、错误、时间和恢复信息。adapter 提供 prepare、simulate、request signature、broadcast、confirm、resume；各链自行定义原始交易和确认逻辑。

状态写入可恢复存储或后端订单，页面刷新后继续查询；幂等键防止重复提交；日志统一但保留 raw error。安全上不持久化签名 secret，前端也不把“已提交”当“已成功”。这种抽象可服务 Mint Forest 奖励、1DEX 批量操作和其他交易产品，但是否落成共享包要看团队和版本耦合，不先做过度平台化。
